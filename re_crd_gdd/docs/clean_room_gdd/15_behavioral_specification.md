# 15. Especificação Comportamental (BDD)

Este capítulo documenta o comportamento esperado do motor de simulação e das ferramentas de edição usando cenários Gherkin (Given/When/Then). Os cenários servem como especificação executável — qualquer implementação (Python editor ou Godot) deve passar em todos os cenários listados.

> **Metodologia**: Os cenários foram derivados do processo de engenharia reversa do formato binário (.LEV, .PAR, .ANM, SOLVE.RES). Cada cenário representa um comportamento observado ou deduzido a partir dos dados e do código de referência em `tim2_editor/`. Consulte `docs/clean_room_gdd/tim2_specs/state-machine-specification.md` para a referência completa da máquina de estados.

---

## Feature: Physics Simulation Loop

O motor de simulação opera em exactly 60 ticks por segundo (60Hz), executando 7 passes em ordem estrita a cada tick.

### Scenario: State counters advance each tick at 60Hz

- **Given** a level is running in Play mode
- **When** the simulation tick fires at 60Hz
- **Then** the engine executes all 7 passes in strict order: State Counters → Gravity → Behaviors → Viewport Clamp → Collisions → Proximity/Electrical → Constraints
- **And** no pass is skipped or reordered

### Scenario: State counters update animation timers

- **Given** a part with `state_counter = N` and `LIMIT_UPPER = 8`
- **When** the State Counter pass executes
- **Then** if `state_counter != 0`, the engine increments `state_counter` by 1
- **And** if `state_counter >= LIMIT_UPPER`, it wraps to `LIMIT_RESET` (default 0)

### Scenario: Zero-state parts apply random delay

- **Given** a part with `state_counter = 0` (idle state)
- **When** the State Counter pass executes
- **Then** the engine applies a random delay in the range [40, 239] ticks before allowing `state_counter` to advance
- **And** the delay is generated by the LCG RNG seeded per-part

### Scenario: Sub-state countdown before state advance

- **Given** a part with `sub_counter > 0`
- **When** the State Counter pass executes
- **Then** the engine decrements `sub_counter` by 1
- **And** when `sub_counter` reaches 0, `state_counter` is set to `LIMIT_RESET`

### Scenario: Gravity integration applies to unconstrained objects

- **Given** a moving part that is not connected to a rope or belt anchor
- **When** the Gravity Integration pass executes
- **And** the part is not marked as fixed (flags_1 does not have 0x6000)
- **Then** the engine applies gravitational acceleration to `vel_y` based on the level's `gravity` value
- **And** the acceleration is looked up from the gravity tier table for the part's category

### Scenario: Gravity direction respects level settings

- **Given** a level with `gravity` set to a specific value (default 272)
- **When** the Gravity Integration pass executes
- **Then** all non-fixed parts receive the same `gravity_y` direction (downward)
- **And** if `flags_3` bit 3 is set (wind), `gravity_x` may be non-zero

### Scenario: Special behaviors execute per part type

- **Given** a part with a defined behavior handler (e.g., motor, cannon, animal AI)
- **When** the Behaviors pass executes
- **Then** the engine calls the appropriate behavior handler for that part type
- **And** the handler may modify `pos_x`, `pos_y`, `vel_x`, `vel_y`, or `state_counter`

### Scenario: Viewport clamping prevents parts leaving screen bounds

- **Given** a moving part with position `pos_x, pos_y`
- **When** the Viewport Clamp pass executes
- **And** `pos_x < 0` or `pos_x > viewport_width` or `pos_y < 0` or `pos_y > viewport_height`
- **Then** the engine clamps the position to the viewport boundary
- **And** if the part hit the floor (pos_y > max), it bounces with COR applied to `vel_y`
- **And** if the part hit the ceiling (pos_y < 0), `vel_y` is negated

### Scenario: Gravity field clamp at maximum values

- **Given** a level with gravity value
- **When** the gravity vector magnitude exceeds `±0x2600` or `±0x3000` depending on the phase
- **Then** the engine clamps the gravity to the maximum allowed value
- **And** the clamped value is used for all subsequent gravity integration passes

### Scenario: AABB collision detection finds overlapping pairs

- **Given** two parts A and B with bounding boxes
- **When** the Collision pass executes
- **And** the AABB of A overlaps the AABB of B (axis-aligned bounding box intersection)
- **Then** the engine registers a collision event between A and B
- **And** it repositions both parts to eliminate the overlap along the minimum separation axis
- **And** it applies an impulse to both parts' velocities based on the Coefficient of Restitution (COR)

### Scenario: Interconnected parts skip collision with each other

- **Given** two parts A and B where A is connected to B via rope or belt
- **When** the Collision pass executes
- **Then** the engine skips collision detection between A and B
- **And** the `connected_1` / `connected_2` fields are checked to determine skip eligibility

### Scenario: Collision response applies COR-based velocity impulse

- **Given** two parts A and B in collision with overlap vector and normal
- **When** the Collision pass calculates the response
- **Then** the engine computes the relative velocity along the collision normal
- **And** applies an impulse magnitude of `J = -(1 + COR) * rel_vel_n / (1/mA + 1/mB)`
- **And** adds `J * normal` to each part's velocity

### Scenario: Proximity detection activates electrical conduction

- **Given** a part with electrical capability (generator, outlet, switch)
- **When** the Proximity & Electrical pass executes
- **Then** the engine checks all connected parts in the electrical network
- **And** propagates the electrical state through the connection chain
- **And** activates any part whose `connected_N` index references an electrified source

### Scenario: Laser beam traces line-of-sight to first obstacle

- **Given** a laser emitter (part type 91, 92, or 93) in active state
- **When** the Proximity & Electrical pass executes
- **Then** the engine casts a ray from the emitter in the laser's direction
- **And** checks for intersections with obstacle parts (walls, mirrors, detectors)
- **And** the beam travels until it hits a target or reaches maximum range

### Scenario: Laser activates detector when beam intersects

- **Given** a laser beam path intersecting a laser-activated plug (part type 96)
- **When** the Proximity & Electrical pass validates line-of-sight
- **Then** the detector part transitions to active state
- **And** any part connected to the detector receives electrical current

## Feature: Constraint Systems

Os sistemas de constraint (cordas e correias) são resolvidos no passo 7 do loop de simulação.

### Scenario: Rope maintains maximum distance between anchors

- **Given** a rope part (part type 10) connecting anchor A and anchor B
- **And** the rope has a defined maximum length (stored in the `behavior` field of the rope part)
- **When** the Constraint Solver pass executes
- **Then** the engine computes the current distance between A and B
- **And** if the distance exceeds the maximum rope length, it corrects the positions of A and/or B to satisfy the constraint
- **And** the correction moves the anchor that is not fixed (non-0x6000 flags)

### Scenario: Single-pass rope solver corrects only when stretched beyond limit

- **Given** a rope connecting two parts A and B
- **When** the current distance between A and B is less than or equal to the rope's maximum length
- **Then** the engine makes no corrections (passive constraint)
- **And** when the distance exceeds the maximum, the engine applies a single correction step

### Scenario: Pulley redirects rope force vector

- **Given** a pulley part (part type 7) with a rope passing over it
- **When** the Constraint Solver pass executes
- **Then** the engine treats the pulley as a redirection point for the rope
- **And** the effective distance becomes the sum of rope segments on each side of the pulley
- **And** force is transmitted through the pulley to the other rope segment

### Scenario: Belt synchronizes angular velocity across all connected parts

- **Given** a belt part (part type 8) connecting multiple gears and motors
- **When** the Constraint Solver pass executes
- **Then** the engine sums the torques from all driving parts (motors with positive torque)
- **And** distributes the same angular velocity `±60px/s` standard to all driven parts
- **And** the sign of velocity depends on the relative orientation of the belt connection

### Scenario: Belt angular velocity locked at ±60px/s standard

- **Given** a belt with at least one driving part (motor, pinwheel, etc.)
- **When** the Constraint Solver calculates the belt angular velocity
- **Then** the resulting angular velocity is locked to the standard `±60px/s`
- **And** all parts connected to the belt receive the same absolute angular velocity
- **And** the direction (sign) is preserved from the driving part's orientation

### Scenario: Electrical current conducts through connected chain

- **Given** an electrical network with a power source (generator, solar panel, outlet)
- **When** the Proximity & Electrical pass executes
- **Then** the engine traverses the connection graph starting from the power source
- **And** for each connected part, it sets the electrical state based on the source
- **And** parts with `outlet_plugged_1` or `outlet_plugged_2` referencing the source become active

## Feature: State Machine Execution

A máquina de estados governa transições visuais e lógicas das peças. Consulte `docs/clean_room_gdd/tim2_specs/state-machine-specification.md` para referência completa.

### Scenario: state_counter increments each tick when not zero

- **Given** a part with `state_counter = N` where N > 0
- **When** the State Counter pass executes
- **And** the part's `sub_counter == 0`
- **Then** the engine increments `state_counter` by 1
- **And** if the new value reaches `LIMIT_UPPER`, it wraps to `LIMIT_RESET`

### Scenario: state_counter wraps at LIMIT_UPPER to LIMIT_RESET

- **Given** a part with `state_counter = LIMIT_UPPER - 1` (typically 7 when LIMIT_UPPER = 8)
- **When** the State Counter pass increments the counter
- **Then** `state_counter` becomes equal to `LIMIT_RESET` (typically 0)
- **And** the animation state resets to the initial visual state

### Scenario: SOLVE.RES trigger fires when self AND other states match

- **Given** a collision between part A and part B
- **And** part A is in state `self` (from SOLVE.RES entry)
- **And** part B is in state `other` (from SOLVE.RES entry)
- **When** the Collision pass resolves the interaction
- **Then** the engine looks up the SOLVE.RES table entry for the pair (A.state, B.state)
- **And** if a matching entry exists, it overrides `state_counter` of the target part to `anm_state`

### Scenario: Collision with null anm_state uses trigger self value directly

- **Given** a SOLVE.RES entry where `anm_state` is null
- **When** the trigger condition is satisfied (self AND other states match)
- **Then** the target part's `state_counter` is set to the trigger's `self` value directly
- **And** no override to a different state occurs

### Scenario: SOLVE.RES explicit anm_state overrides trigger chain

- **Given** a SOLVE.RES entry where `anm_state` is explicitly set
- **When** the trigger condition fires
- **Then** the target part jumps to the specific `anm_state` regardless of the current position in the trigger chain
- **And** this overrides the default sequential progression

### Scenario: Orphan ANM states exist but are never reached by SOLVE.RES

- **Given** an ANM file with state IDs that are not referenced in any SOLVE.RES entry
- **When** the simulation runs
- **Then** those orphan states are never reached through collision triggers
- **And** they serve only as internal transition frames in continuous animations
- **And** the engine logs a warning about orphan states during level load (SM4 validation)

### Scenario: Broken trigger chains do not crash the simulation

- **Given** a SOLVE.RES entry referencing a non-existent part type or state
- **When** the trigger condition would fire
- **Then** the engine gracefully skips the invalid entry
- **And** the simulation continues without crashing (SM5 validation)

### Scenario: State limits vary by part type

- **Given** a part with custom state limits (e.g., LIMIT_UPPER != 8)
- **When** the State Counter pass executes for that part
- **Then** the engine uses the part-specific limit values from the lookup table at segment 0x5B41
- **And** 17 parts are known to require custom limits beyond the default of 8

## Feature: Solution Conditions

O sistema de avaliação de vitória verifica condições quando a simulação está em execução.

### Scenario: state_match condition triggers when part reaches target state

- **Given** a solution condition of type `state_match` targeting part P with target state T
- **When** the simulation runs and part P's `state_counter` reaches T
- **Then** the engine marks the condition as satisfied
- **And** all solution conditions are checked at each tick

### Scenario: AABB overlap condition triggers when part center enters target region

- **Given** a solution condition of type `AABB_overlap` defining a target rectangle and a part P
- **When** the simulation runs and the center of part P falls within the target rectangle
- **Then** the engine marks the condition as satisfied
- **And** the target rectangle is defined in level coordinates (pixels)

### Scenario: Multi-condition requires all conditions simultaneously satisfied

- **Given** a solution condition of type `multi_condition` containing N sub-conditions
- **When** the simulation evaluates the solution
- **Then** all N sub-conditions must be satisfied simultaneously
- **And** if any sub-condition fails, the overall condition is not met

### Scenario: Level completes when all solution conditions are met

- **Given** a level with a set of solution conditions
- **When** all conditions transition to satisfied state
- **Then** the engine displays the victory screen
- **And** the simulation halts (physics freezes, win dialog appears)

## Feature: Editor Tool Modes

O editor de níveis em Godot (ou o protótipo Python) implementa modos de ferramenta que controlam a interação do usuário com o canvas.

### Scenario: MODE_PLACE instances part at grid-snapped position

- **Given** the user is in MODE_PLACE (shortcut P)
- **When** the user clicks on the viewport canvas
- **Then** the editor snaps the click position to the nearest 16x16 pixel grid
- **And** instances a new part node at that position with default appearance
- **And** the part is added to the scene tree under PartContainer

### Scenario: MODE_PLACE shows ghost preview following cursor

- **Given** the user is in MODE_PLACE with a part type selected
- **When** the mouse cursor moves over the viewport
- **Then** the editor displays a semi-transparent ghost sprite of the selected part
- **And** the ghost follows the cursor position in real-time

### Scenario: MODE_PLACE rejects placement on overlap with active parts

- **Given** the user is in MODE_PLACE and hovers over an area occupied by an existing active part
- **When** the user attempts to click and place a new part
- **Then** the editor highlights the ghost in red (modulate = red)
- **And** rejects the placement, keeping the part in the catalog
- **And** parts with type >= 150 (scenery) are exempt from this check

### Scenario: MODE_SELECT reveals contextual handles on selected part

- **Given** the user is in MODE_SELECT (shortcut S)
- **When** the user clicks on an existing part in the viewport
- **Then** the editor selects that part and displays contextual handles
- **And** the handles include Flip, Delete, and Program buttons appropriate to the part type

### Scenario: Flip handle rotates part or mirrors axis per part type

- **Given** a part selected in MODE_SELECT with a Flip handle available
- **When** the user clicks the Flip handle
- **Then** the editor rotates the part by 90° or mirrors its axis (X or Y)
- **And** updates the `flags` field of the part to reflect the new orientation
- **And** the behavior changes accordingly (e.g., cannon fires in new direction)

### Scenario: Delete handle removes part from scene

- **Given** a part selected in MODE_SELECT with a Delete handle available
- **When** the user clicks the Delete handle
- **Then** the editor removes the part node from the scene tree
- **And** frees the node memory with `queue_free()`

### Scenario: Program handle opens modal dialog for logical settings

- **Given** a programmable part selected in MODE_SELECT (laser, balloon, timer, switch)
- **When** the user clicks the Program handle
- **Then** the editor opens a modal dialog appropriate to the part type
- **And** user settings (color, text, delay ticks, initial state) are saved to the part's properties

### Scenario: MODE_CONNECT draws elastic line from anchor to cursor

- **Given** the user is in MODE_CONNECT (shortcut C)
- **When** the user clicks on a valid anchor point of part A (rope, belt, or electrical)
- **Then** the editor begins drawing an elastic Line2D from anchor A to the cursor
- **And** the line follows the cursor in real-time

### Scenario: Valid connection anchor highlights green during drag

- **Given** the user is in MODE_CONNECT and dragging a connection line
- **When** the cursor passes over a valid connection anchor (compatible type)
- **Then** the anchor highlights green (snap magnetic assistance)
- **And** the line snaps to the anchor position

### Scenario: Invalid connection target highlights red

- **Given** the user is in MODE_CONNECT and dragging a connection line
- **When** the cursor passes over an incompatible connection anchor
- **Then** the anchor highlights red
- **And** releasing the mouse does not create a connection

### Scenario: MODE_CONNECT registers belt_connected_part or rope_connected_part IDs

- **Given** the user completes a connection in MODE_CONNECT by clicking on a valid target anchor
- **When** the connection is validated
- **Then** the editor writes the target part's ID to `connected_1` or `connected_2` of the source part
- **And** for ropes: `rope_connected_part` indices are updated
- **And** for belts: `belt_connected_part` indices are updated
- **And** for electrical: `outlet_plugged_1` / `outlet_plugged_2` indices are updated

### Scenario: Box selection selects multiple parts in drag rectangle

- **Given** the user is in MODE_SELECT and drags a rectangular selection box
- **When** the drag is released
- **Then** all parts whose AABB intersects the selection box become selected
- **And** multi-select handles appear for group operations (move, delete)

## Feature: Simulation Controls

O controle de simulação gerencia a transição entre o modo de edição e o modo de jogo.

### Scenario: Play serializes level state and starts 60Hz physics loop

- **Given** the editor is in edit mode with a level loaded
- **When** the user clicks the Play button (or presses Space in preview mode)
- **Then** the editor serializes the current parts array to `temp_state.yaml`
- **And** switches to simulation mode, starting the 60Hz physics loop
- **And** all gizmos and handles are hidden

### Scenario: Stop halts physics and restores parts to exact pre-play positions

- **Given** the simulation is running (physics loop active)
- **When** the user clicks the Stop button
- **Then** the engine halts the physics loop
- **And** reloads the parts from `temp_state.yaml`
- **And** restores all positions, velocities, and states to the exact pre-play values
- **And** returns to edit mode with gizmos visible

### Scenario: Fast Forward accelerates physics at 2x/4x speed

- **Given** the simulation is running
- **When** the user clicks the Fast Forward button
- **Then** the engine accelerates the tick rate to 2x (120Hz) or 4x (240Hz)
- **And** all physics calculations scale accordingly
- **And** the visual rendering updates at the accelerated rate

### Scenario: Reset returns all parts to initial YAML state

- **Given** the simulation has run for N ticks
- **When** the user clicks Reset (or Stop then reloads the level)
- **Then** all parts are restored to their initial state from the loaded YAML
- **And** `state_counter` values are reset to initial values
- **And** `pos_x, pos_y, vel_x, vel_y` are restored to YAML values

## Feature: Level Persistence

A persistência de níveis permite salvar e carregar níveis em formato YAML.

### Scenario: Save exports current parts array to YAML with all fields

- **Given** the editor has a level in memory (loaded or newly created)
- **When** the user clicks Save (or Ctrl+S)
- **Then** the editor serializes the entire level to a `.yaml` file
- **And** includes: `level_info` (magic, background, title, goal), `environment` (gravity, pressure, music_track), `hints` array, `fixed_parts` array, `moving_parts` array
- **And** each part entry contains: `part_type`, `x`, `y`, `appearance`, `flags` (flag_1, flag_2, flag_3), `dimensions`, `physics` (behavior, belt_anchor, rope anchors, connections)

### Scenario: Load reconstructs part instances from YAML with full fidelity

- **Given** a valid `.yaml` level file exists
- **When** the user clicks Load and selects the file
- **Then** the editor parses the YAML and reconstructs all part instances
- **And** validates the magic number (`EF AC 13 01` or `14 01`)
- **And** populates all fields: part_type, position, appearance, flags, physics properties
- **And** throws an error for invalid or corrupted YAML

### Scenario: New warns when unsaved changes exist

- **Given** the editor has unsaved changes to the current level
- **When** the user clicks New (or Ctrl+N)
- **Then** the editor displays a confirmation dialog warning of data loss
- **And** if the user confirms, the current level is cleared
- **And** if the user cancels, the current level is preserved

### Scenario: Level info editing preserves all metadata fields

- **Given** the user presses the I key to open the Level Info dialog
- **When** the dialog displays the current level metadata (title, goal, gravity, pressure, music_track, hints)
- **Then** the user can edit all 6 fields (title, goal_description, gravity, pressure, music_track, active_hints_count)
- **And** Tab navigates between fields, Enter confirms, Escape cancels
- **And** the changes are saved to the in-memory level state

### Scenario: Level save uses YAML blocking structure matching decoder format

- **Given** the editor serializes a level for save
- **When** writing the YAML output
- **Then** the output matches the format consumed by `timgres/decoder/d_puzzle.py`
- **And** part entries use the blocking structure: `part_type`, `x`, `y`, `appearance`, `flags`, `flags_meanings`, `dimensions`, `physics`
- **And** connection fields are written as `connected_1`, `connected_2`, `outlet_plugged_1`, `outlet_plugged_2`
